# Work with /m:os - Brand Manager

Start from the consumer project, not the design-system package directory.

Use `npx --no-install mos-brand` when the local executable is not on PATH. `--help`, `-h` and `--version` work before project configuration. `self-test` checks a shipped synthetic consumer without changing the real project.

1. Run `mos-brand doctor`. If this is a new consumer, run `mos-brand init`, then ask for the missing identity, what/how/why and JTBD in `.mindrian/intake.json`. Do not invent answers. Run `mos-brand configure --intake .mindrian/intake.json`.
2. Read `.mindrian/WORKFLOW.md` and `.mindrian/APPLICATION-PLAN.md`. Preview `mos-brand adopt`, then apply the workflow reference when authorized. A reference installs instructions; it does not prove the team follows them.
3. Identify the active participant and responsibility when this changes the handoff. An optional `consumer.participants` list can name people, teams and agents; never invent identities or reviews. Route from the actual work, not a persona title. Direct, inherited, baseline and adjacent directives retain their stated authority and scope. Read only the needed branch, not every descendant.

Run `mos-brand context`. Read the returned shared rules and relevant segment contracts. Load canonical artifacts only for the current job. Preserve the nested relationships and the original source home. Never replace the brand book with recalled memory.

Work the structure, room by room. Every segment that context returns is an ICM room with the same five files: ROOM.md (identity, one job), INDEX.md (routing to a smaller segment or an artifact), CONTEXT.md (inputs, process, outputs, human check), STATE.md (status, artifact count) and dated entries (the canonical artifacts). Context also returns each segment's job, inputs, process and state path. Walk a direct segment in full, an inherited one for its constraints, an adjacent one within its declared scope, the baseline always; stop when the job is served. Treat the process in CONTEXT.md as the procedure for that part of the work and the human check as its acceptance test: quote it in the run's review stage with evidence. Keep the cited segment beside every decision. Where a segment is thin or silent, apply the voice, the positioning and the stops, name the gap in the missing-material list and return it as a proposed entry for the book; never fill it with an invented or imported rule.
For homepage or long-form project scrollytelling, read the canonical `experience/scroll` SKILL.md returned by context before choosing effects. Follow its procedure and supersession rules, including the React hybrid flipbook ruling when architecture transforms. Use aligned frames and editable SVG under one scroll timeline; a new frame sequence must be authored and reviewed separately. A flipbook means many closely spaced successive images, not a few dissolves or a single image with moving overlays. Preserve the selected generated artwork and its visual quality. Declare `homepage` for homepage work and reconfigure if the scope changes. The React homepage is an implementation reference, not automatic production approval.

Use `mos-brand catalog --kind font` or `mos-brand catalog --query logo` to find exact selected assets. Read their owning guidance for role, license and status before using `asset` to copy. Never infer approval from a file appearing in the catalog.

For generated artwork, read the selected `teams/image-creation/generation/prompts` SKILL.md and GUIDE.md. For blog art, begin with `mos-brand image brief --article posts/article.md`, read the selected editorial STYLE.md and develop an original composition from the article. Use style guidance, not fixed rooms, stairs or the triangle. The editorial brief does not require the full quest story. For project explainers, begin with `mos-brand image brief`; ask its missing meaning questions before choosing a treatment. Complete the explanatory answers, including uncertainty, a conditional future and the next move. Then use `mos-brand image templates` for discovery and `mos-brand image prompt --brief brief.json` to compile. Read the resulting explanationPlan before generating. Pass `--recent previous-prompt.json` for collection variation or sequence continuity; never diversify frames within a flipbook. Save the compiled record with `--out`, then generate and review the actual image separately.

Critical: do not hand off substantial written content as a wall of text. Provide a meaningful scan path with restrained rich text and useful visual explanation, and record the actual editorial review.

For written content, apply the resolved `writing/text-augmentation` procedure: outline first, assign text roles, preserve evidence in the scan path, adapt Hebrew direction and review accessible reading. Its numeric defaults are brand starting points, not research-proven conversion claims.

Run `mos-brand checklist` for the selected contracts and human checks. Run `mos-brand review --file path/to/draft.md` on a Markdown, text or HTML draft. Exit 1 reports a blocker or command failure; exit 2 requires human review even when no heuristic signal was found. The scan does not inspect React components, rendered CSS or the truth of claims. Do not use its result as brand approval.

For articles, technical writing and social content, read the selected `writing/editorial-integrity` SKILL.md and relevant child GUIDE.md. Distinguish notes, limitations, real warnings and own summaries from direct quotations. Open original supporting material, preserve quote wording and context, test technical instructions and retain qualifications when shortening. Use `review --file draft.md --evidence ledger.json` for declared-record checks, not as proof of truth.

4. Use `mos-brand run start` for reviewable production. Each numbered stage has a contract and editable `output/`. Ask the reviewer to examine each output before recording `run approve`. An approval record is an attestation, not verified identity. Never invent a review or use the agent's name to impersonate one.
5. Explain the actual checks at handoff. Report draft, proposed, conflicting or unspecified material and pending UI/UX rules accurately. Doctor compares the installed source and local managed files; it does not check remote releases. Deliberately update the private package to receive upstream brand changes. After updating the installed package, preview `mos-brand refresh`, then use `mos-brand refresh --apply` to refresh unedited managed guidance. Edited files remain protected; copied assets and old runs are not rewritten. Run doctor again. Reconfigure after scope changes.
6. Return useful learning with `mos-brand memory remember --text "..."` if memory is configured. Include the source and uncertainty. Recalled learning can suggest a change; only canonical source changes can change the rules.

If the executable is not on PATH, use `npx --no-install mos-brand` from the consumer project. The CLI provides context and records workflow evidence. It does not create polished content by itself or guarantee brand compliance.

For drafting blog posts, social posts, newsletters, landing pages, releases or case studies, use the canonical `skills/draft-content/SKILL.md` artifact returned by context (resolved from the package source root) Mindrian adapter and the resolved `teams/marketing/draft-content` GUIDE.md. Technical writers use its scan and evidence procedure alongside the documentation playbook. The upstream reference is archived, not an alternative source of brand rules.

Before drafting or revising substantial content, invoke the automatically installed `mindrian-draft-content` project skill and read its local `references/brand-context.md`. Use a content run and prepare the real piece brief before prose. This is a required procedure, not optional further reading. The CLI enforces the managed brief-stage transition; it cannot intercept arbitrary writing outside its workflow.

Before blogs, images, visual aids or animation, invoke the automatically installed mindrian-production skill. Inspect task requirements with tools check, install supported missing tools, then prepare the explanatory brief and actual brand instructions. Unknown external skills need an official source or verified host setup. A static guide needs no React runtime; a required interactive or scroll explanation must not be flattened because a matching component is unavailable.

For work that selects the website-google-access ruling, read context.websiteAccess and the active experience/forms/access guide before creating navigation, CTAs, onboarding or access code. Google sign-in applies only where the MindrianOS website needs a signed-in identity (the account page, the Theo connection consent and letter preferences), followed by an optional introduction; the blog, articles, installation pages and documentation stay open. Continue without answering skips the introduction after login; it never skips authentication. Apply the named scope, keep marketing permission separate and report actual deployment/security verification independently. This supersedes earlier introduction-only access guidance.

For web, homepage, app-UI or visual-aid work that wants a new CSS capability (interpolate-size, gap decorations, anchoring and anchored queries, scroll-driven or scroll-triggered animation, scroll-state queries and the rest), read the proposed experience/css-capabilities guide and capabilities.json first. The capability is an enhancement over a semantic base that works without it, behind a feature test and an off switch, with a tested fallback and a reduced-motion branch. Support statements carry a date and a source; the ones in the book were checked on 2026-10-23 against MDN browser-compat-data and local Chromium and Firefox builds (WebKit and phones not run). The room is active guidance and its scoped ruling is proposed, so report no compliance result until the owner rules; only interpolate-size and gap decorations are first-wave, and the other eight stay lab, prototype, tracking or required-now. Report the browser checks actually run. CSS motion in production needs the preflight contract; native CSS scroll stays lab only until an adapter and renderer contract exist.
