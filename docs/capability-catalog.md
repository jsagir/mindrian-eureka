# Capability catalog

The catalog exposes user jobs, not package folder names. These methods serve an intelligence system built to explore uncertainty—especially wicked challenges—for opportunity. Capability calls are instruments in that exploration; none should force one problem frame or imply that a complex challenge has been solved. Each capability must have a manifest, input/output schema, runtime declaration, network/data classification, known limitations, provenance, and an evaluation plan before it is enabled. See [Engine jobs and when to use them](engine-jobs.md) for the method context, plain-language descriptions, and family-level readiness.

The machine-readable version of this catalog is packaged at `src/mindrian_eureka/data/capability-catalog.v1.json` and is served through the top-level `eureka` CLI and `scout_capabilities`. A catalog entry can be blocked or planned; it does not imply that a corresponding runnable engine is present. For each algorithm service's source lineage and rationale, see the [algorithm origins and rationale register](algorithm-origins-and-rationale.md).

Runnable entries include a `routes` object with the exact CLI executable and MCP tool to invoke. CLI `arguments` show positional request-file placeholders, with required options and environment settings called out where needed. MCP `arguments` show the generic workflow dispatch fields or the dedicated request wrapper; asynchronous jobs list their status and result tools under `follow_up_tools`. Call `eureka capability <capability-id>` or `scout_capability_contract` to retrieve that route alongside its JTBD, readiness, and input/output schemas. Planned and blocked entries intentionally have no invocation route.
