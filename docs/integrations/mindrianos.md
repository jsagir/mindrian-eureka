# MindrianOS host integration contract

This contract defines how MindrianOS should use the `mindrian-eureka` repo through `/mos:eureka` and MCP. The local knowledge graph is part of MindrianOS: it is the canonical, evolving knowledge layer that its own workflows and authorized Eureka engines need to inspect. Eureka is an engine service attached to that layer, not a second graph owner. The engine MCP exposes the same capability definitions and contracts as the CLI.

**Integration status (verified 2026-10-20):** The local Eureka catalog contains 67 capabilities: 59 `experimental` or `host_brokered` entries have CLI and MCP routes, and 8 `blocked` or `planned` entries intentionally have none. The MindrianOS `feat/eureka-adapter-rebased` branch contains graph projection, catalog dispatch, async job lifecycle, and direct CLI guidance. Live catalog verification confirms all 59 advertised MCP routes and schemas, and all CLI route families; live dispatch checks exercise representative shared and dedicated services plus all planned/blocked boundaries. Live room tests confirm bound-session authorization, read-only graph projection, lineage, and unchanged room data. The current MindrianOS Plugin worktree adds five dedicated graph-discovery adapters listed below; those additions are not committed or released. The integration is **not merged into MindrianOS main or released**. The local Eureka `main` branch contains two commits ahead of its origin remote. The active `/mos:eureka` research-planner perspective remains a separate surface. Direct engine calls can be used independently; no full-planner-to-catalog workflow is required. Real-user evaluation and release integration remain outstanding.

## MindrianOS graph as the shared knowledge layer

MindrianOS remains authoritative for graph identity, room scope, authorization, provenance, human review, and persistence. Eureka engines interact with graph knowledge through a MindrianOS-authorized graph projection: the host selects the room/portfolio scope and focal context, preserves stable graph IDs and source references, and sends only the bounded node/edge or artifact data needed by the selected method. Graph-aware engines can return candidate relations or analysis signals that refer back to those stable IDs. MindrianOS resolves those references, traces evidence, and decides whether to record a proposal or accepted relation through its existing workflow.

**Verified in the local MindrianOS Plugin checkout (2026-10-19):** room graph state lives at `<room>/.mindrian/room.db`; `/mos:eureka` already reads its bound room's graph and ICM structure through the research-planner `eureka` perspective. Graph reads are expected to use MindrianOS's navigation boundary. `navigation.getGraphExport` exists, but it is a visualization export with a strict display whitelist: it omits raw node properties, source paths, and node text. Therefore, it is not an engine input and must not be repurposed to expose broad room content.

The engine repo implements the **engine-side snapshot contract** (`graph.explore_local_relationships`, `graph.propose_relationships`, `graph.map_neighbourhoods`, `graph.prepare_artifact_bundle`, and other selected graph methods). The MindrianOS integration branch provides `eureka_graph_project` for a standalone projection, `eureka_graph_analyze` for graph relationship exploration, `eureka_graph_propose_relationships` for the stable proposal alias, `eureka_graph_map_neighbourhoods` for structural analogy mapping, `eureka_graph_backtest` for temporal method evaluation, `eureka_graph_score_surprise` for prior/posterior belief-change triage over selected claims, `eureka_graph_compare_topics` for selected two-corpus comparison, `eureka_graph_rank_paths` for verifying and ranking host-retrieved graph paths, `eureka_graph_package_relationships` for source-bound pending proposals, `eureka_graph_prepare_artifacts` for building the shared source-linked input contract used by text engines, `eureka_graph_opportunity_scout` for running RS+HSI over that authorized bundle, `eureka_graph_genesis_plan` for a local graph-to-Genesis research plan, and `eureka_hsi_interpret_whitespace` for HSI interpretation using selected local Framework/ProblemType relations. The current Plugin worktree adds `eureka_graph_find_shared_neighbor_gaps`, `eureka_graph_find_network_holes`, `eureka_graph_find_community_bridge_pairs`, `eureka_graph_assess_category_edge_patterns`, and `eureka_graph_find_similar_unlinked_items` for five independent graph-discovery algorithms. The tools resolve the bound room through MindrianOS, project only caller-selected IDs through the navigation boundary, start the local `eureka-mcp` stdio server, and verify response capability/scope/snapshot identity. They require `MINDRIAN_EUREKA_ROOT` to point to the engine checkout and `uv` to be available. Analysis results are proposals or plans for Theo/MindrianOS review. These tools do not perform external research or write to the graph; the RS+HSI opportunity scout invokes Eureka’s configured local encoder, and its output remains an unvalidated candidate shortlist. They do not replace or mandate the separate `/mos:eureka` research-planner flow. A caller-supplied snapshot is the transport shape; it is not a separate graph or a replacement for MindrianOS. The direct `eureka-graph --neo4j` option remains a development/replay path for a separately configured Neo4j dataset, not a reader for the room-local SQLite graph.

### Current host-side graph projection adapter

The MindrianOS integration branch's `eureka_graph_project`, `eureka_graph_analyze`, `eureka_graph_propose_relationships`, `eureka_graph_map_neighbourhoods`, `eureka_graph_backtest`, `eureka_graph_score_surprise`, `eureka_graph_compare_topics`, `eureka_graph_rank_paths`, `eureka_graph_package_relationships`, `eureka_graph_prepare_artifacts`, `eureka_graph_opportunity_scout`, `eureka_graph_genesis_plan`, and `eureka_hsi_interpret_whitespace` tools read the active bound room through MindrianOS's read-only navigation door. All require explicit node IDs and project only those nodes and induced edges; map additionally requires distinct base and target nodes to be selected. HSI interpretation additionally requires upstream whitespace zones and 2D projection, with every referenced framework and room artifact included in the selected IDs. Its `ADDRESSES_PROBLEM_TYPE` and `FEEDS_INTO` input rows are derived from projected MindrianOS edges (with only allowlisted `effectiveness`, `confidence`, `transform`, `created_at`, `evidence`, `pws_confidence`, and `quarantine_source` metadata); problem types are not inferred from text. The graph projection is `mindrian.engine-graph-projection.v3`. The adapter suite passed 11/11 serially, and current live tests include catalog route/schema coverage, partial-projection reporting, real resolver refusal of unbound and registry-fallback sessions, authorized bound-session analysis, and async cancellation with child-process exit. Parallel live cancellation has not been proven reliable. Authorization through a real active user session remains unverified; bound-room integration tests use an isolated synthetic room and session binding. The RS+HSI adapter uses the configured encoder extra through `uv`; its model must already be available locally because Eureka does not download models during a run. The adapter tools:

- bind to the already-resolved room and preserve room/snapshot identity;
- apply authorization, focal scope, and node/edge/resource caps before emitting content;
- emit stable node IDs, node types, labels, selected text/title, source references, content hashes, relevant typed edges, and explicit omitted/excluded counts;
- bind `scope_id`, `snapshot_id`, and projection version in snapshot metadata; keep that exact scope on result contracts so the host can reject stale or cross-scope results;
- avoid filesystem paths, credentials, unrelated room content, restricted-room metadata, and unrestricted raw properties;
- reports missing IDs, excluded system nodes, nodes with no allowlisted text, text truncation, and edge truncation; marks the snapshot incomplete when any of these conditions occurs and uses a content-derived snapshot ID over the selected projection;
- distinguish semantic relations from containment, membership, and evidence/provenance edges;
- return the engine result to MindrianOS for source resolution, existing review, and filing; never grant Eureka direct write access.

In the adapter review implementation, graph relationship exploration and structure mapping use `eureka_graph_analyze` and `eureka_graph_map_neighbourhoods`. Artifact-based text engines use `eureka_graph_prepare_artifacts` to return the catalog-defined artifact contract, then route that bundle through the selected capability's contract and prerequisites. The bridge requires `MINDRIAN_EUREKA_ROOT`, `uv`, and the checkout's MCP extra. All adapter results preserve `scope_id` and `snapshot_id`. These are method-specific projections of one MindrianOS graph, not independent copies or graph authorities.

In a checkout containing the adapter review implementation, launch the MindrianOS MCP server with the engine checkout configured in its environment, for example:

```sh
MINDRIAN_EUREKA_ROOT=/absolute/path/to/mindrian-eureka node scripts/mindrian-mcp-server.cjs
```

On Windows PowerShell, set `$env:MINDRIAN_EUREKA_ROOT` to the checkout path before launching the MindrianOS MCP server. The bridge starts a fresh local Eureka stdio process per analysis call; it does not need the engine MCP added as a second external host server.

```json
{"node_ids":["claim:...","evidence:..."]}
```

Then pass the returned `snapshot`, `scope_id`, and `snapshot_id` to the selected Eureka tool. The projection tool rejects unbound sessions, missing room identity, unknown fields such as `room_path`, and unsafe node-ID syntax. It does not add neighbors implicitly.

Graph interaction has two useful directions:

1. **Graph → engines:** MindrianOS supplies a bounded, versioned snapshot or artifact projection. Structural graph methods inspect nodes and relations; text-oriented engines can receive eligible graph nodes via `graph.prepare_artifact_bundle`, then analyze them using their own method contracts. The complete projection result can be sent directly to the combined `eureka-signal-scout` CLI input (legacy alias: `eureka-scout`) or MCP `scout_start_opportunity_signal_scout` request; both preserve the host scope and snapshot IDs while RS and HSI analyze the same source-linked artifacts.
2. **Engines → graph workflow:** graph exploration returns endpoint IDs, proposed status, method signals, host `scope_id` and `snapshot_id` when supplied, a SHA-256 fingerprint of the exact supplied snapshot, capability version, run configuration, and limitations. The artifact-bundle projector rejects a requested scope that conflicts with the snapshot's host scope. These fields bind results for host review; they do not authenticate the caller or grant authorization. The MindrianOS run record should bind that result to its own ICM run ID and preserve the engine's uncertainty caveats. MindrianOS resolves IDs and evidence, applies its review gate, and performs any write. Engine results are not graph mutations.

### Which engines consume the MindrianOS graph

The graph is the MindrianOS part of the system. Eureka engines should work *with* it through host-authorized input and result contracts; they must not each open `room.db`, maintain a competing graph, or assume a Neo4j service is the canonical store. Not every method needs the same projection, and a graph-derived input should retain stable MindrianOS IDs so results can be resolved back to their evidence.

This means graph interaction is a platform contract shared across the engine catalog, not a promise that every engine independently traverses the graph. The smallest host integration slice is: (1) MindrianOS prepares one authorized snapshot/projection from its local graph, (2) Eureka runs one selected compatible capability, and (3) MindrianOS resolves the returned IDs and presents candidates through its existing review path. Keep all three steps bound to the same room/snapshot and ICM run record.

The adapter must preserve MindrianOS's distinction between containment, membership, evidence, and semantic relations. Eureka's current undirected focal radius is only an analysis projection; it is not a canonical Holon boundary, authorization check, or graph-navigation policy. Cross-room discovery is allowed only when MindrianOS has authorized the combined scope and its provenance rules permit that use.

## The two surfaces and their authority

| Surface | What it means in MindrianOS | Owns | Must not do |
|---|---|---|---|
| `/mos:eureka` in the MindrianOS plugin | The existing user-facing conversation and workflow. MindrianOS resolves the active room, clarifies the discovery objective, calls Theo/framework guidance when useful, and decides which capability to hire. | Room binding, user intent, scope, approval cards, Theo, `/mos:status`, `/mos:find-connections`, `/mos:qualify-opportunity`, ICM, graph and portfolio writes. | Treat a similarity-ranked pair as an opportunity; bypass room gates; silently run every engine. |
| `eureka-mcp` | The MindrianOS host's callable capability service. The host sends an authorized, bounded artifact bundle or graph projection and calls the job/capability tools. | Capability discovery, input validation, bounded computation, job state, engine/runtime metadata, and source-linked candidate results. | Resolve a room path, expand scope, fetch outside research, call Theo, or write to MindrianOS graph/portfolio. |
| `eureka-pair-scout` / `eureka-structure-mapping` / `eureka-decision-sequences` CLI programs | Direct, operator-facing engine interfaces for local development, reproducible runs, and environments where a prepared bundle is already available. Legacy acronym commands remain aliases. | Their named computation over explicit input files. | Claim to be the complete `/mos:eureka` workflow or substitute for MindrianOS room authorization and review. |

The `/mos:eureka` research-planner perspective and catalogued engine tools are complementary, independently callable surfaces. They do not form a mandatory workflow. A raw CLI invocation does not acquire MindrianOS room context by itself; MindrianOS must prepare the same authorized scoped bundle and preserve approval and filing steps. If it cannot do that, it reports the integration as unavailable instead of silently changing behavior.

MCP gives MindrianOS a stable tool boundary. It does not provide room access, Theo's judgment, user approval, external research, or graph persistence. No capability may infer permission from `scope_id` or `research_grant_id`; MindrianOS validates those before sending data.

The repo's workflow specification is [the MindrianOS opportunity-discovery workflow](../../src/mindrian_eureka/data/mos-opportunity-discovery.v1.json). It is published as `scout://workflows/mos-opportunity-discovery` and through the `scout_host_workflow` MCP tool for a connected host to inspect. The `/mos:eureka` research-planner adapter should treat it as the handoff contract: Eureka performs the selected computation and returns the next host action; MindrianOS executes its own native command and approval workflow. Eureka does not issue slash commands on the host's behalf.

For a local Genesis plan, MindrianOS can pass the `artifacts`, `scope_id`, and `snapshot_id` from `graph.prepare_artifact_bundle` to `research.run_genesis_local_plan`. The resulting source manifest keeps graph IDs and references available for review. Theo may review heuristic domain suggestions before MindrianOS executes returned queries through its approved research broker. This capability performs no remote search, no model call, and no graph write. The SME cross-domain discovery and verification workflow is described separately in [cross-domain research](../engines/cross-domain-research.md). Combining that workflow with `research_run` requires a separate host composition and is optional; the capability tools can be called independently.

For a container launch, configure MindrianOS to invoke the repository's `scripts/run-mcp-container` executable over stdio. Set `MINDRIAN_EUREKA_RS_MODEL_PATH` to a local model directory and `MINDRIAN_EUREKA_DATA_DIR` to the writable job/cache directory in the server process environment. Build the `mindrian-eureka:local` image first. The container has no network, so the model must already exist on the host.

## `/mos:eureka` user journey

1. **Read room state.** Resolve the active room once through MindrianOS's room resolver. Read `/mos:status` and relevant room material so the scout starts from current, room-bound context. A status summary is a navigation aid, not proof that a section is empty; include explicitly selected source files such as the JHTV catalog when they are outside the status index.
2. **Frame the wicked challenge.** Preserve the user's desired decision, constraints, exclusions, and evidence standard while keeping uncertainty, connected system parts, and competing problem frames visible. Treat uncertainty as territory to explore for opportunity, not merely noise to remove. Theo may guide method choice. Ask a focused question only when a missing answer changes scope, data handling, or method choice.
3. **Select capabilities.** Read `scout_capabilities`; choose only capabilities that fit the job and whose maturity/prerequisites are acceptable. Do not run every engine by default. Explain the job in user language and show which sources it will inspect.
4. **Prepare the scoped bundle.** MindrianOS supplies stable artifact IDs, resolvable source references, titles, content hashes, text, and corpus labels. It records the exact input snapshot and excludes unrelated files. It never passes room paths, credentials, or the entire room directory to a worker.
5. **Plan and approve.** Call `scout_plan`. Present the objective, room/snapshot, input counts, selected capability, model/runtime, expected outputs, limits, and any data-transfer implications. Obtain whatever room-policy approval applies before starting. For a local-only run, explicitly state that content stays on the local execution boundary; model download is a separate choice.
6. **Run and monitor.** Call `scout_start`, keep the returned `job_id`, and use `scout_status` while it runs. Offer `scout_cancel` if the user stops or changes scope. A failed, blocked, or partial result must remain distinct from “no opportunities found.”
7. **Inspect candidates.** Call `scout_result`. MindrianOS resolves the returned `source_ref`s into room links and presents the actual source evidence, method/version, limitations, and uncertainty. Retrieval/similarity signals are leads, not opportunity evidence.
8. **Connect and challenge.** For selected candidate pairs, MindrianOS can use `/mos:find-connections` to trace relationships and evidence in its graph. If outside evidence is needed, Theo/MindrianOS frames the questions and the host's research workflow obtains the relevant approval and sources; Eureka does not fetch them. SME mapping or verification is a distinct next capability, not an automatic truth check.
9. **Qualify and preserve.** Present a candidate to `/mos:qualify-opportunity` only after its source trail and counterevidence are available. The user makes the qualification/disposition decision. MindrianOS writes an approved proposal with lineage and retains rejected/parked reasons; Eureka never writes to the room graph or portfolio.
10. **Accumulate.** Preserve each run's snapshot and proposal identifiers so MindrianOS can deduplicate, relate, revisit, and deepen candidates across rooms. A run may add to a portfolio; it does not replace the portfolio with only the room currently open.

For a catalog-scale run such as JHTV, the host first normalizes each catalog item to one stable artifact record and preserves its source URL, category path, extraction date, and input hash. Eureka processes the complete authorized snapshot, returns a bounded candidate set with both source IDs, and reports coverage and skipped/uncertain records. MindrianOS then uses its connection, research, and qualification flows on selected candidates. The whole-catalog pair ranking is only the discovery pass; the researched portfolio is the decision product.

If the user asks for `/mos:status`, `/mos:find-connections`, or `/mos:qualify-opportunity`, MindrianOS performs those host workflows itself. Eureka may recommend the next one, but must not simulate its result or claim to have invoked it unless the host actually did so.

## Tool contract

- `scout_capabilities` and `scout://capabilities`: capability name, JTBD, prerequisites, limits, and maturity.
- `scout_host_workflow` and `scout://workflows/mos-opportunity-discovery`: the host-owned `/mos:eureka` stages, boundaries, and approvals.
- `scout_plan(request)`: validates a supplied bundle and returns analysis stages, model identity, and counts. It does not execute or fetch research.
- `scout_start(request, idempotency_key?)`: starts a durable job and returns `job_id`, state, scope ID, and retention duration.
- `scout_status(job_id)` / `scout_result(job_id)` / `scout_cancel(job_id)`: job lifecycle and output retrieval.
- `scout_record_review(review)`: records `useful`, `direction_correct`, and `already_known` judgments for a result candidate.
- `scout_evaluation_report()`: descriptive judgment aggregates separated by method and task snapshot/objective.
- `scout_delete_job(job_id)` / `scout_clear_embedding_cache()`: user/host requested data cleanup.
- `scout_sme_prepare_research(request)`: freeze exact mechanism-discovery or per-inference verification queries for the host approval UI.
- `scout_sme_validate_research_bundle(request)`: check exact query/source/claim lineage in the host-returned bundle, not the truth of approval.
- `scout_sme_map(request)`: run local deterministic structural mapping on source-claim-linked inputs.
- `scout_sme_finalize(request)`: validate reviewer assessments and return cited inference records; it does not file them.
- `decision_compare_sequence_patterns(request)`: compare a human- or Theo-coded decision sequence under caller-supplied HMM models. The host must obtain consent, retain the feature-coding provenance, and present the result as unvalidated relative model fit rather than a person score.
- `decision_fit_sequence_patterns(request)`: exploratory Baum-Welch fitting from at least two coded traces and an explicit seed model, with at least 32 total observations. The result is unvalidated; never use it to assess, rank, or diagnose people.

For cross-domain pair finding, the CLI and MCP call the same method implementation and result contract, but their execution lifecycles differ: `eureka-pair-scout` (legacy alias: `eureka-rs`) is a direct bounded run that reads an explicit JSON bundle; MCP provides the durable `plan → start → status/result/cancel` job lifecycle. Both return the same `host_handoff` guidance. The other engine CLIs execute their named method and are not yet unified under the RS job lifecycle. Handoff guidance recommends a next host action; it does not execute a `/mos:*` command, grant approval, or write graph state. The MindrianOS host must preserve the same scope manifest, model identity, source references, approval rules, and result caveats whichever execution surface it uses. Never pass an arbitrary filesystem path through an MCP request; never use a direct CLI call to avoid a MindrianOS gate.

Input is bounded at 2,500 artifacts and 20 MiB of UTF-8 artifact text. Each artifact needs a unique ID, source reference, non-empty text, and `room` or `external` corpus. A host should split exceptionally large rooms into explicit snapshots rather than silently truncate them.

## External research and confidentiality

`external` and `hybrid` requests require a `research_grant_id` and appropriately labeled external artifacts. The ID is audit metadata only; this server does not verify the grant. MindrianOS must validate the grant, user approval, source terms, room scope, and allowed model path before sending the bundle. Research discovery/fetching remains a separate host service. The RS server performs no network research calls and does not write to room or portfolio state.

The job database temporarily holds the submitted request while it runs. Terminal jobs clear their saved request; completed results retain bounded excerpts and source references for up to 30 days. Embeddings are cached separately as derived sensitive data. Align the data-directory placement, encryption, retention, and deletion with room policy.

## Theo and ICM

Theo is the MindrianOS reasoning and framework service used by the host workflow. The host may consult Theo's framework, concept, and review guidance while framing the work and challenging candidate mechanisms. In the current available Theo MCP surface, these calls provide general method guidance; they do not accept the arbitrary JHTV case bundle, run `/mos:find-connections`, evaluate a specific opportunity, or write to the room graph. Therefore the host must not label a candidate “Theo-reviewed” unless Theo has actually been given and reviewed that case through an available case-capable interface. A generic Theo review guide is a rubric, not case evidence.

The engine MCP does not call Theo directly. MindrianOS owns Theo calls, room context, ICM run records, and graph/portfolio state. ICM can record the plan, stage artifacts, and decisions. The committed MindrianOS feature branch exposes the separate catalogued engine calls; it does not replace or automatically compose the existing `/mos:eureka` research planner, and it has not yet been released.
