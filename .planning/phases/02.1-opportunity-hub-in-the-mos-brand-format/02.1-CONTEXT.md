<domain>
## Phase Boundary

After `eureka run` on a folder of sources, one command writes one local hub page with three views: opportunity bank, connection graph, full catalogue (search and filter). It reads only the run output and its manifest. It makes no network call. Requirements: HUB-01 to HUB-05.

Out of scope here: `/mos:eureka` wiring and the replay rebuild (Phase 3), the full public dataset and the reproduction guide (Phase 4), new scoring or new engines, any claim of novelty or value.

Engine names in user-facing text: "Find Unusual Pairs Across a Research Collection" and "Rank Unusual Pairs by Wording and Meaning". Never bare "RS" or "HSI" on the page.
</domain>

## Implementation Decisions

### Brand process (HUB-02)
- **D-01:** Plan 1 is the brand intake. Run `mos-brand init`, complete the intake (identity, what, how, why, JTBD) for surfaces `website` and `app-ui`, run `configure`, then `adopt`. Draft the intake from PROJECT.md; the owner confirms it. The earlier README intake (design system 2.7.0, `docs/brand-application.md`) is stale and is superseded. Source: `segments/governance/intake/ROOM.md`, `skills/mindrian-job-ux-ui/SKILL.md`.
- **D-02:** `docs/brand/hub-design-decisions.md` lists every choice (colour, type, layout, motion, Theo face) with the cited segment path and the `mos-brand context` output line. `mos-brand review --file <hub page>` must pass before the phase closes. A person approves before anything publishes (brand stop).
- **D-03:** Where the book is silent, do not guess. Record it as "book silent, proposed segment" in the decisions file and return the gap to the book. Silent items so far: offline vendoring of a script library (D-12), password gate (D-17), the filed/unfiled idea for a pairs-only tool (D-14).

### Views and data model (HUB-01)
- **D-04:** One page, three views with the same selection shared across them. Views and their questions: Opportunity bank = "Which pairs should a person look at first?" (ranked list from both engines, with a filter by engine). Connection graph = "Who sits next to whom?" (page title is the question, per graph guide section 1). Catalogue = "What is in the collection?" (all records, search by ID, title word or text word, filter by source file and by whether the record appears in any pair).
- **D-05:** Earn the graph first. The graph view shows only when the run has about 15 or more records with at least one pair. Below that it draws a static diagram. Source: `segments/experience/graph-visualization/entries/2026-10-21/GUIDE.md` section 1.
- **D-06:** Data travels as `hub-data.js` (`window.HUB = {...}`), not fetched JSON, so the page opens from disk inside an enclave. Shape follows `network-data.schema.json`, extended for pairs.
- **D-07:** Deterministic build. The hub writer is code only: no LLM text, no random values, stable sort with ID tie-break, so two builds from the same run folder are byte-identical (same rule as RUN-04). Hub file hashes are recorded next to the run manifest.
- **D-08:** Reading-panel text is built from record fields and fixed templates only. The graph guide asks for written stories per node; Eureka cannot, because it is offline and deterministic. The panel shows: record title, source file and source reference, the pair partner(s), both scores with the score-meaning note, which engine ranked it, the "candidate, not verified" label. A link goes to the source record. Panel is `aria-live="polite"`.

### Graph (book segments `experience/graph-visualization`, `foundations/color`)
- **D-09:** Marks. Record = member sphere. Pair = line. Meaning-and-wording disagreement pair from the wording engine and structure pair from the unusual-pairs engine are two line kinds, always named in words in the legend, tip and panel ("proposed connection, wording engine, score 0.62"). Never colour alone.
- **D-10:** Colour meaning from the book: cobalt `#1F3FBF` = inquiry or a route under inspection; red `#D6281F` = an assumption under challenge; yellow `#F2C200` = possibility, ink label chip only, never yellow text on paper; ink `#111111`; paper `#F7F5EE`; quiet `#ECEAE2`. Candidate pairs are unverified connections: dashed line plus the printed word "Proposed". A blue route is attention, not proof.
- **D-11:** Neighborhoods: weighted label propagation over pair links, ties sorted by ID (deterministic). Weak pairs hidden by default below each engine's named floor, floors printed on the page.
- **D-12:** Library. The reference uses `3d-force-graph` loaded from jsDelivr. That breaks HUB-01 (no network). Vendor one pinned copy (`3d-force-graph@1.79.1`, at least two weeks old, license file kept) into the hub output folder and load it by relative path. Add a test that fails if the page contains any `http(s)://` load or any `fetch` of a remote URL. Book silent on offline vendoring, so propose a segment (D-03). If WebGL or the library fails, the page falls back to the list of pairs (graph guide section 7).
- **D-13:** Geometry follows meaning (brand rule 20). Spheres and curves in the graph are fine; do not force square nodes. Hard edges stay on panels and gates.
- **D-14 (OWNER-WORD, recommended default):** Eureka output has no "filed" or "bridge" idea (that is JHTV room vocabulary). Default: records are members; ranked pairs are the opportunities; a "bridge" is a record that has top pairs into two or more neighborhoods, labelled "Possible bridge" with an ink chip, never "eureka". Alternative: drop bridges entirely in 2.1.
- **D-15:** Data check panel, quiet, on the page (graph guide section 4): count of identical-text records, empty-text records, shared-boilerplate families, and what was removed or flagged. Reuse the run's own corpus report if present; do not recompute scores.

### Look, type, layout (HUB-02)
- **D-16:** Tokens come from `foundations/tokens` (copy `asset-b1c43da20b.css` unchanged). Fonts: Figtree display, DM Sans body and UI, JetBrains Mono for IDs and scores; bundled files copied into the output folder (offline). Layout: 12-column grid, 24 px gutters, 1200 px inner maximum, tablet 6 columns, phone 4 columns with 20 px gutters; logical properties so right-to-left works later; cards only for bounded objects; reading prose stays open; 4 px spacing steps. Source: `segments/experience/layout`, `segments/foundations/typography`.
- **D-17 (OWNER-WORD, recommended default):** Password gate (HUB-04). A page-side check alone is not security. Default: option `--password-env NAME` encrypts `hub-data.js` payload with WebCrypto (AES-GCM, key from PBKDF2 of the passphrase, salt and iterations stored in the file). The page asks for the passphrase and shows the Theo "Boundary" state until unlocked. Documented honestly as protection of the file at rest, not of a machine that already holds the passphrase. Without the option the page is not gated. Book silent (D-03).
- **D-18:** Labels. Every claim and every opportunity shows "candidate, not verified" and a source link; a test fails on any item missing either (HUB-03). Fact, inference and proposal use the book's role labels (13 px word plus line treatment). The page states: a pair means two records read similarly in one way and differently in another, not that anything is new, wanted or valuable.
- **D-19:** Copy is plain English, short sentences, no em dashes, no walls of text (rules 1 and 13). Scannable hierarchy; the top pairs come first.

### Theo face and motion
- **D-20:** Theo face states from `identity/theo/states`: header = Handover ("work is ready for the person", does not mean the project is complete); empty result = Limit; locked = Boundary; idle = Rest. Never Found (it can imply correctness) and never Challenge on a candidate. MindrianOS leads; Eureka is an adjunct and has no registered signature mark, so the page carries the exact parent lockup unchanged as an endorsement and "MindrianOS Eureka" as text (`docs/brand-application.md` decisions still hold; rules 2 and 3).
- **D-21:** Motion (rules 19 and the shaper motion ruling). The reference's red particles on bridge links are an ambient loop, which rule 19 forbids. No ambient motion. Motion only on a person's action (fly to a selected node, "Show me the bridges" tour), through one shared player, with a complete readable still, and none under `prefers-reduced-motion` (no dead still/pause control then). Any new CSS capability is an enhancement with a feature test, an off switch and a tested fallback (rule 21).

### Accessibility
- **D-22:** WCAG 2.2 AA target. 44 px targets, 3 px focus ring, 13 px minimum label (checked at 320, 390, 768, 1280, 1600; fails only below 13 px at 1024 and up). Contrast uses the book pairs. Text and every list view work without JavaScript or WebGL. The 3D stage has an `aria-label` that points to search and the lists. Phone: guide collapses, panel becomes a bottom sheet. Source: `segments/experience/accessibility`.

### Example and reproduction (HUB-05)
- **D-23:** 2.1 ships a small public-data fixture and reproduces the three JHTV views (opportunity bank, idea graph, October leads page) in the new format from it. The full public dataset, expected hashes and guide stay in Phase 4 (EXM-01, EXM-02). No private room data in the repo. The JHTV room files are a structural and visual reference only; nothing is copied from them (CONTRIBUTING: no private room exports, no personal names).

### Claude's Discretion
- Module layout under `src/mindrian_eureka/hub/`, command name (default `eureka hub RUN_DIR --out DIR`, optional `eureka run --hub`), internal data schema, search index shape, test layout. Python rules from Phase 2 D-skill list still apply (typed, ruff, mypy strict on new modules).
- Which public fixture to use, provided its license allows redistribution (record it).
</decisions>

## Existing Code Insights

### Reusable Assets
- Run outputs: `unusual-pairs.json`, `wording-and-meaning-pairs.json`, `ranked-pairs.md`, `manifest.json`, `run-info.json` (run-info is the only file allowed to differ between runs; the hub must not read it for content).

- Manifest hashing and canonical writer from Phase 2: reuse for hub file hashes.
- mos-brand graph reference files (`network.template.html`, schema, derive script) as the structural starting point.

### Established Patterns
- Offline and deterministic: no network, no LLM, seeds and versions recorded.
- Plain-English engine names; "candidate, not verified" on every output.
- Tests in `tests/`; staging folder then atomic rename for output.

### Integration Points
- New `hub` command beside `run` and `doctor` in `src/mindrian_eureka/cli.py`.
- Reads a finished run folder; never writes into the source folder or the run folder (writes a sibling `hub/` or `--out`).
