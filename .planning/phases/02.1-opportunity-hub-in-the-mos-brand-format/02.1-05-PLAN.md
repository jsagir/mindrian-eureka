<objective>
Turn typed run data into the hub payload: normalized weights, neighborhoods, cut-offs, bridges, the data check, line widths and source links. Add the guard that fails the build when an item lacks the label or a source link.

Purpose: HUB-01 (data for the three views) and HUB-03 (every claim and opportunity carries the label and a source link; a function fails when one does not).

Output: model.py, verify.py, a written rules file, two test files.

Locked decisions this plan implements:
- D-04, D-05: the payload feeds three views with one shared selection. `graph.earned` is true when at least 15 records appear in a visible pair.
- D-07: deterministic, stable sort with ID tie-break.
- D-08: the panel fields are record fields and fixed templates. This plan adds 4-decimal score text exactly as ranked-pairs.md prints it.
- D-09, D-10: the payload keeps the two engines apart. The page names the engine on every pair.
- D-11: weighted label propagation over pair links, ties by ID, weak pairs below each engine's named floor hidden by default, floors printed.
- D-14 (OWNER-WORD default): bridges are labelled "Potential eureka". The word "eureka" is never used as a label for a bridge or a result. The product name "MindrianOS Eureka" in the header and footer is allowed.
- D-15: data check from the run's own files, no score recomputed.
- D-18: label on every item (HUB-03).

Resolutions of UI-SPEC section 17 that this plan makes and records in docs/brand/hub-model-rules.md:
- Open point 3 (where the cut-offs live): `manifest.settings.unusual_pairs.min_percentile` and `manifest.settings.wording_and_meaning.min_percentile`. Both engines already apply their percentile gate when they run, so with default settings no returned pair lies below its own floor. A pair is "weak" only if it carries `scores.percentile` below a floor greater than 0. The control "Show weaker pairs" exists only when the payload holds at least one weak pair. The page still prints each floor (B05, B06).
- Open point 5 (bridge rank across two scales): scores are normalized inside each engine to the range 0 to 1 and a record uses the engine that gives it the higher sum.

  <behavior>
    - Weight of a visible pair = max(rank_score, 0) divided by the largest max(rank_score, 0) among the visible pairs of the same engine. If that largest value is 0, every weight is 0.
    - Edge weight between two records = the sum of the weights of their visible pairs over both engines.
    - Label propagation: nodes are the records in at least one visible pair, sorted by ID. Start with each node as its own label. Pass over the nodes in sorted order. A node takes the label with the largest summed edge weight among its neighbors. If the current label ties for the largest, it keeps it. Other ties go to the smallest label string. Stop after a pass without a change, or after 100 passes.
    - Neighborhoods are the groups of nodes with the same final label, numbered 1, 2, ... by size (largest first), ties by the smallest record ID. `tint` is NEIGHBORHOOD_TINTS[(number - 1) mod 21].
    - A pair crosses when its two records are in different neighborhoods. Width: crossing pairs get WIDTH_CROSSING. Other visible pairs get WIDTH_MIN plus (WIDTH_MAX minus WIDTH_MIN) times (score minus lowest visible score of that engine) divided by (highest minus lowest); when highest equals lowest the width is WIDTH_MAX. Weak pairs get weight 0.0 and WIDTH_MIN.
    - Shuffling the input pairs gives identical hoods and widths.
  </behavior>
