<objective>
Add the optional password gate: the Python encryption, the build option, the unlock script and style, and tests that prove interop with real browsers.

Purpose: HUB-04. A page-side check alone is not security (D-17). The default design encrypts the data, so a copied file at rest holds no readable record text. The honest limit is written down.

Locked decisions this plan implements:
- D-17 (OWNER-WORD default): `--password-env NAME` encrypts the `hub-data.js` payload with WebCrypto-compatible AES-GCM and a key from PBKDF2 of the passphrase; salt and iterations are stored in the file; the page shows the Theo Boundary state until unlocked; the file protects data at rest, not a machine that already holds the passphrase; without the option the page is not gated. If the owner changed this default in plan 01, follow the owner's answer in docs/brand/hub-design-decisions.md.
- D-07: byte-identical builds, so salt and nonce are derived, not random. Record the weakness honestly (PATTERNS risk 5).
- D-20: Boundary face while locked, Handover after unlock (UI-SPEC section 10).
- D-22: the form has a visible label, a 44 px field, Show/Hide as a 44 px button, Enter submits, focus starts in the field, a polite status line.

Design (the derivation, written in words so the code and the record agree):
- Plaintext: the canonical JSON bytes of the payload (the same bytes `js_assignment("HUB", payload)` would embed).
- Salt: first 16 bytes of SHA-256 over the ASCII text `eureka.hub.gate.salt.v1` followed by the 32 raw bytes of the run manifest sha256.
- Key: PBKDF2-HMAC-SHA256 over the UTF-8 passphrase and the salt, 600,000 iterations, 32 bytes (`hashlib.pbkdf2_hmac`, standard library).
- Nonce: first 12 bytes of HMAC-SHA256 with the key as HMAC key over the ASCII text `eureka.hub.gate.nonce.v1`, the salt and the SHA-256 of the plaintext. A different plaintext or key gives a different nonce, so a nonce is never reused with different data under one key.
- Cipher: AES-256-GCM (the `cryptography` library). Associated data: the ASCII text `eureka.hub-envelope.v1|600000`, so a changed iteration count fails the tag. The ciphertext includes the 16-byte tag at its end, the layout WebCrypto expects.
- Envelope (the value of `window.HUB_ENVELOPE`): schema, kdf (name, iterations, salt as base64), cipher (name, nonce as base64), ciphertext as base64.
- The probe in plan 04 proved this layout decrypts in Chromium and Firefox from a file URL. Use the derivation recorded in docs/brand/hub-probe-results.md if it differs in a detail, and say so in the gate record.

| Boundary | Description |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02.1-65 | Information disclosure | Passphrase in a flag, a log, a file or an error | mitigate | No flag takes the value. Messages name the variable, never the value. Tests scan all written files and captured streams for a distinctive passphrase. |
| T-02.1-66 | Information disclosure | Record text in a locked hub | mitigate | The locked page is rendered without a payload; `hub-data.js` holds only the envelope; tests search every file for ids, titles, text fragments, counts and the fingerprint. |

| T-02.1-68 | Cryptographic failure | Nonce reuse with different data | mitigate | The nonce is an HMAC over the key, the salt and the plaintext hash, so data or key changes change it; test with 1,000 plaintexts. |
| T-02.1-69 | Cryptographic failure | Offline guessing of a weak passphrase | accept | Cost per guess is 600,000 PBKDF2 rounds. A short passphrase warns at build time. The record states plainly that the gate protects at rest and is only as strong as the passphrase. |
