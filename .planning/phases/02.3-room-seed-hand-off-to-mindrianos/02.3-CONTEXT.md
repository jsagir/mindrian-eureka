<domain>
## Phase Boundary

Today MindrianOS feeds Eureka: a room graph projection goes in, candidate pairs come out. This phase builds the other leg: a candidate intersection from a Eureka run becomes a seed that MindrianOS can open as a room. Eureka writes the seed, deterministically, with no model and no network. MindrianOS consumes it through its own room-birth chokepoint (`/mos:ignite`, excavate path) in a separate phase of the plugin repo. The contract between the two is a versioned file, `eureka.room-seed.v1`, so a later MindrianOS version can consume seeds written today.

In scope: the seed contract and its JSON schema; `eureka seed <run> --pair <id>` and `eureka seed <run> --cluster <record-id>`; a hub action that names the seed command for a pair; the column-to-section map as data in the mapping file; the "what we know" and "what to feed next" lists computed from filled and blank columns and from the dictionary's "not in this export" list; pair seeds and cluster seeds; candidate selection by pair class and node degree in the pair graph.

Out of scope: any write into a MindrianOS room, registry or `room.db` (SEED-117: a room is born only through the plugin's chokepoint); any model call; any ranking change; the plugin-side `/mos:ignite --from-seed` (its own GSD phase in the MindrianOS-Plugin repo, which this phase's contract doc must make plannable).
</domain>

<decisions>
## Implementation Decisions

### D-01 The seed is a contract, not a package
- Schema id `eureka.room-seed.v1`, one JSON file plus evidence files in one folder. The folder is NOT a room: no ROOM.md, no STATE.md, no registry entry. It is a bundle the plugin excavates.
- Seed JSON holds: `seed_kind` (`pair` or `cluster`), the run's `scope_id`, `snapshot_id`, `manifest_sha256`, engine versions, the pair ids or the spine record id, `pair_class` and the carried outcome columns of every record in the seed, the opportunity statement draft (reuse `opportunity.prepare_statement`; its output stays labelled `candidate, not verified` and `critic: pending`), `source_refs` with content hashes, `known` (filled columns grouped by room section) and `feed_next` (blank columns and the "not in this export" items grouped by room section, each with the one-line reason), and a `suggested_sections` list in order.
- Evidence files: one markdown file per record with the excerpt the run already carries (`review_context.left_evidence` / `right_evidence`), the source ref and the content hash; no full text copy beyond what the run output holds.

### D-02 Column-to-section map is data in the mapping file
- The mapping file (Phase 2.2 `examples/mappings/technology-audit-export.json`) gains an optional `room_sections` block: `{ "<section>": ["<column>", ...] }`. For the partner export: `problem-definition` <- `problem_solved`, `end_user`, `marginal_or_groundbreaking`; `market-analysis` <- `size_of_unmet_need`, `target_companies`; `solution-design` <- `abstract`, `topics`, `stage_work_required`; `legal-ip` <- `status`, `licenses`, `options`, `first_license_or_option_date`, `licensed_to_jh_startup`, `licensed_externally`; `financial-model` <- `funding_total`, `translational_total`, `follow_on_total`, `startup_funding_after_deal`, `corporate_partnership_amount`; `funding` <- `had_translational_funding`, `translational_funds`, `had_follow_on`, `follow_on_summary`; `team` <- `lead_inventor`, `licensing_associate` (people columns go to the room's team section only, never into engine text or pair payloads).
- `not_in_export` is a list in the same block, each item with its target section and the external source named in the dictionary: patents -> `legal-ip` (Inteum), royalties and license income -> `financial-model` (Inteum), true disclosure date -> `legal-ip` (Inteum).
- `feed_next` for a record = every mapped column that is blank in that record, plus every `not_in_export` item. `known` = every mapped column that is filled. No inference, no model.

### D-03 Which intersections get a seed
- A pair seed for any pair in the run output. The hub action and the CLI accept a pair id.
- A cluster seed for a spine record: a record whose degree in the run's pair graph (both engines, deduplicated by pair key) is at least 3 (default, settable). The cluster holds the spine plus its paired neighbours; each neighbour becomes an opportunity-bank entry in the seed; the spine fills the sections.
- `eureka seed <run> --list` prints the candidates: cross-class pairs first (an open record next to a licensed one; a routing room), then open-open pairs (bundle candidates), then cluster spines by degree, each with its pair class counts. Ties break by record id. The list is a suggestion in numbers; a person picks.

### D-04 Hub action
- The hub bank shows, per pair, the exact `eureka seed` command for that pair (copy text, no execution from the page; the hub stays static and offline). Reuse the hub's existing chip and label components; no new visual design; `mindrian-job-ux-ui` rules the row.

### D-05 Plugin-side consumption (contract only in this phase)
- `docs/room-seed-contract.md` describes, for the MindrianOS-Plugin repo, how `/mos:ignite --from-seed <folder>` should excavate a seed: birth the room through the existing chokepoint (`/mos:rooms new <slug>`), file the evidence into the mapped sections, write each seeded section's BRIEF with the `feed_next` line as the first move, file the opportunity statement into `opportunity-bank` at `review_status: proposed`, and land on the F.1 card. The first step on that surface follows the Hooked rule: one room, one question. This doc is the input to the plugin phase; it writes nothing on the plugin side.
- The doc states the model boundary plainly: the seed is offline and the partner's; working the room with Larry sends room content to the model provider; the partner decides.

### D-06 Determinism and labels
- Same run, same pair, same seed bytes (hash recorded). The seed JSON records the engine versions and the run manifest hash. Every seed keeps `candidate, not verified`.
