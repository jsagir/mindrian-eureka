# Phase 02.3 Plan 02: Seed contract and the pair seed Summary

**`eureka seed <run> --pair <id>` reads a hash-checked run and writes one deterministic folder (`seed.json` plus one evidence file per record) that follows the closed schema `eureka.room-seed.v1`; known and feed-next lists come from cell states with no inference, and the statement draft stays `candidate, not verified`, `critic: pending`, `banked: false`.**

## Accomplishments

- Closed schema `room-seed.v1.json` (Draft 2020-12). `if/then/else` on `seed_kind` closes `selection`; `if/then/else` on `held_in` allows `value` only for `carried`; `oneOf` makes a feed item either `column` or `item` with `source`. `critic`, `banked` and `review_status` are consts. The file does not hold the label text.
- `seed` package, 8 modules, no numpy and no network or process import. `builder.assemble_seed` takes members, pair groups and bank entries, so plan 02.3-03 reuses it for cluster seeds.
- `seed.json` holds every key of the contract; same run and pair give the same bytes (tested across two separate run builds). The summary prints the sha256 of `seed.json`.
- Evidence files follow the 15-line format; the fence grows with the longest backtick run in the excerpt; title and path-like fields are collapsed to one line so a title cannot add markdown lines above the untrusted-text line.
- `tests/seed_support.py::make_seed_run` builds a seedable run (cell states, section map, classes) with the Phase 2 writers.

## Decisions (the three CONTEXT mismatches)

1. **Derived ids.** The run holds no `scope_id` or `snapshot_id`. The seed derives them (see key-decisions). Plan 02.3-05 must state that they are derived.
2. **Evidence source.** Pair files carry no `left_evidence`. The excerpt is the first 1600 characters of the record text in the run corpus file.
3. **Statement draft (OPEN QUESTION for the owner, default taken).** `opportunity.prepare_statement` cannot run on run data. The in-package draft keeps the gate fields and says so in `basis`. If the owner wants the real tool, the run needs dimension scores and a host rank first.

## Deviations from Plan

**1. [Plan text error] "same seed bytes" for a pair listed in the opposite order by the other engine**
- **Found during:** Task 1 test design
- **Issue:** Swapping left and right in a pair file changes that file's hash, so the manifest hash differs, so `manifest_sha256` and `scope_id` differ by design. Also the synthetic score helper depends on the order of the two indexes.
- **Fix:** The test writes the run once, swaps left and right of one pair in the wording file with `edit_json` (manifest hash fixed), and compares the documents with `manifest_sha256` and `scope_id` removed, plus the evidence bytes. They are equal.
- **Files:** `tests/test_seed_pair.py` (commit `97c6f69`)

**2. [Plan text error] "no `file:` in the seed bytes"**
- **Found during:** Task 3
- **Issue:** The evidence format has the line `- Source file: <path>`, which contains `file:` by contract. The grep was a false positive.
- **Fix:** The test checks for `file://` instead, plus the run path, the temp path and `/home/`.
- **Files:** `tests/test_seed_command.py` (commit `a0c81fd`)

**3. [Rule 1 - Bug] Label literal in the help text**
- **Found during:** Task 3 check of the label count
- **Issue:** The first help notes typed `candidate, not verified`, which made the count 5.
- **Fix:** The notes use the imported `LABEL` (count back to 4).
- **Files:** `src/mindrian_eureka/seed/command.py` (commit `a0c81fd`)

**4. [Plan detail] `merge_lists` takes a section order**
- The plan listed `merge_lists(per_record)`. It needs the section order, so it takes `order` (a sequence of section names); `source.combine_maps` builds the order when two records resolve different maps.

**5. [Plan detail] Schema error text**
- `validate_seed` names the JSON path and the rule keyword, not the first jsonschema message, so that a title or value never appears in an error.
