<objective>
Make every status read a pure read and move recovery behind one explicit call. Opening the store no longer rewrites rows; `get` no longer deletes; the new `scout_recover` tool is the only path that closes an orphan row.

Purpose: the plugin polls `scout_status` every 250 ms (`eureka-capability-run.cjs:115-135`) and starts one engine process per job session. Today the second process's startup marks the first process's running job as `failed`, `server_restarted` (`jobs.py:94-95`, `:101-108`), and a status read can delete a row (`jobs.py:151-153`). Criterion 2 of the ROADMAP.

Output: `tests/test_job_status_read_only.py`, the store changes, the `scout_recover` tool, one RED commit and one GREEN commit.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| second engine process -> shared `jobs.sqlite3` | A process start must not change the rows of another process. |
| plugin host -> `scout_recover` | An explicit write path; it closes rows that no live process runs. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-04 | Tampering | `JobStore._init_db` | mitigate | no recovery, expiry or resubmit on open (Task 2 Steps 2 and 6) |
| T-06-05 | Tampering | read methods | mitigate | `PRAGMA query_only=1` on every read connection; a write raises (Task 2 Step 1) |
| T-06-06 | Denial of service | `scout_recover` | accept in this plan | until plan 06-03 adds the lock probe, a recover call from a second process can close a row of a live process; plan 06-03 closes this gap and its RED test pins it |
