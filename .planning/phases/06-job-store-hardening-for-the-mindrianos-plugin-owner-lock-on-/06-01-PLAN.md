<objective>
Give the job store a terminal-state guard. A job that reached `completed`, `completed_empty`, `failed`, `blocked`, `cancelled` or `expired` refuses every later state change with a typed `terminal_state` result and changes nothing. Create the shared test seams that the four later behaviour plans reuse.

Purpose: the MindrianOS plugin closes its session on a terminal state (`eureka-capability-jobs.cjs:183-200`). Today a late write moves a finished row back to `running` (`jobs.py:166-183` has no guard), so the plugin and the store can disagree about a job that is over. This plan is first because D-01 and D-02 reuse the refusal shape it introduces.

Output: `tests/job_support.py`, `tests/test_job_terminal_guard.py`, the guard in `jobs.py`, one RED commit and one GREEN commit.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| plugin host -> engine stdio | `job_id` strings and tool arguments arrive from the host; the store must not let a late or repeated call rewrite a finished job. |
| shared `jobs.sqlite3` | Several engine processes write one file; a guard inside one transaction keeps a read-then-write atomic. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-01 | Tampering | `JobStore.transition` | mitigate | read status and write in one connection block; refuse on `TERMINAL` before any write (Task 2 Step 2) |
| T-06-02 | Repudiation | job events table | mitigate | a refused change adds no event, so the event log stays the true history of state changes |
| T-06-03 | Information disclosure | refusal dict | accept | the shape carries only `job_id`, a reason word and a recorded state; no path, no text of the request |
| T-06-SC | Tampering | npm/pip/cargo installs | accept | no package-manager install task in this plan; standard library only (D-09) |
</threat_model>
