# Phase 2.2: Partner export profile and package - Context

**Gathered:** 2026-10-29
**Status:** Ready for planning
**Source:** owner decisions taken in conversation on 2026-10-29 (the discuss step ran in conversation, not as a separate agent)

<domain>
## Phase Boundary

A partner holds a CSV export of a technology portfolio, one row per case number, with text columns that may be blank and with outcome flags, counts and dates (licensed, optioned, funded, follow-on, interest signals). The partner must run Eureka on their own offline machine. The data never leaves that machine. This phase ships what makes that run work and makes the result read right: a mapping for that export, a corpus split from the outcome columns, the outcome columns beside every pair, a case-number join for public marketing text with a coverage line, a partner install guide, and the owner's ruling on partner-internal distribution.

Out of scope: any model call, any network call, any change to the ranking formulas (quick 261029-184 and quick 261029-bfm already landed and ride along), any regeneration of test fixtures, any new hub visual design, and any backtest against outcome dates (that is a later phase; this phase only carries the dates through so a backtest becomes possible).
</domain>

<decisions>
## Implementation Decisions

### The export (PROVEN from the partner's data dictionary, filed in the room on 2026-10-29)
- One row per technology, key column `case_number` (format `C18725`).
- Text columns: `title` (often blank on recent cases), `abstract` (marketing abstract; blank until the partner's production field is set; may hold HTML entities and tags), `topics` (`;` list, `Parent > Topic`, tagging stops October 2019), and the seven inventor answers `problem_solved`, `end_user`, `size_of_unmet_need`, `marginal_or_groundbreaking`, `target_companies`, `stage_work_required`, `funding_invested` (filled on about 26% of cases; some say "See attachments").
- Outcome columns, Y/N unless noted: `licensed_to_jh_startup`, `licensed_externally`, `had_corporate_research`, `had_translational_funding`, `had_any_funding`, `had_follow_on` (Y, N, or `no translational award`); counts `licenses`, `options`, `ndas`, `mtas`, `licensing_deals_lost`, `funding_awards`, `translational_awards`, `follow_on_awards`, `sponsored_research_agreements`, `corporate_partnerships_won`; dates `first_license_or_option_date`, `first_translational_date`, `disclosure_date`; money `funding_total`, `translational_total`, `follow_on_total`, `startup_funding_after_deal`, `corporate_partnership_amount` (blank means none recorded); lists `jh_startup_licensees`, `external_licensees`, `corporate_partners`, `translational_funds`, `follow_on_summary`; status `status` (Active, Inactive, Inactive- Licensed, Passive, Hold), `marketing_status`.
- People columns `inventors`, `lead_inventor`, `ip_manager`, `licensing_associate` exist. They never enter the engine text and never enter a pair payload in this phase (names of people stay out of outputs).

### D-01 Mapping file, not new ingest code (PKG-01)
- `eureka run` already reads CSV through `--mapping <file>` (`src/mindrian_eureka/run/mapping.py`, class `CsvMapping`: `text_columns`, `id_column`, `title_column`, `source_column`, `value_maps`, `labels`). Ship a mapping file for this export under the repo's mapping examples (planner picks the existing location; create `examples/mappings/` only if none exists).
- `id_column: case_number`; `title_column: title`; `text_columns` in this order: `abstract`, `problem_solved`, `end_user`, `size_of_unmet_need`, `marginal_or_groundbreaking`, `target_companies`, `stage_work_required`, `topics`; `labels` give each answer its question as a label so the text reads as prose. `funding_invested` is money talk, not description; leave it out of text.
- Outcome columns, people columns and money columns never appear in `text_columns`. A test asserts it (the mapping file is data; the test loads it and checks the set).
- HTML entities and tags in `abstract` are cleaned by the existing text cleaner (`run/textclean.py`); if it does not strip tags, extend it there, not in the mapping.

### D-02 Outcome class from outcome columns, applied to every engine's pairs (PKG-02)
- Owner clarification 2026-10-29: the package runs EVERY engine that `eureka run` executes on the partner's material (the unusual-pairs engine and the wording-and-meaning engine today, plus any catalog engine the planner finds runnable on a CSV-only corpus without a room), and the hub collects all of their pairs into one opportunity bank in the same format as the existing hub. The outcome split therefore CLASSIFIES pairs; it does not restrict which records an engine sees.
- Add an optional `outcome_rule` to the mapping schema: a column list and a rule. Rule for this export: a record is `licensed` when any of `licensed_to_jh_startup == Y`, `licensed_externally == Y`, `licenses > 0`, `options > 0`, `had_corporate_research == Y`, or `status == Inactive- Licensed`; otherwise `open`. The two class names are fixed: `licensed` and `open`.
- Every engine runs on all records exactly as today. At the output layer (the planner finds the one place both engines' pairs pass through, `run/output.py` or the manifest step), each pair gets `pair_class`: `cross` (one open, one licensed: an open technology next to one that got out), `open_open` (bundle candidates), or `licensed_licensed`. The run summary prints the three counts per engine. The hub shows the class as a label and offers it as a filter view (reuse the hub's existing filter mechanism if one exists; no new visual design).
- Without an outcome rule, behaviour is byte-identical to today (parity tests stay green; the recorded wording params hash stays `bea4c100c2013300` unless the planner records a reason; `pair_class` is absent, not null).
- Do not change `rank_pairs_hybrid_2026`, `rank_pairs`, or `compute_hsi_matrix`. The cross-corpus mode of `opportunity_pairs/runner.py` stays as it is; it is not the mechanism here.
- The percentile gate needs at least 10 eligible pairs per engine; the run must say when the corpus is too small instead of returning nothing silently.

### D-03 Outcome columns on every pair and in the hub (PKG-03)
- Add an optional `carry_columns` list to the mapping. Each record keeps those cells as `extras`; each pair payload carries `left_extras` and `right_extras` with the raw cell strings (no parsing of money or dates beyond trimming). For this export the carried set is the outcome flags, counts and dates listed above, plus `status`; never the people columns, never the list columns that name companies (`jh_startup_licensees`, `external_licensees`, `corporate_partners`), because those name third parties.
- The hub (`src/mindrian_eureka/hub/`) reader refuses unknown schemas and unknown reading sentences (`hub/reader.py`, decision D-08 of Phase 2.1). Extras are additive: the planner must read `hub/contracts.py` and `hub/reader.py` and extend the contract so a run with extras loads and a run without extras still loads. The hub shows extras as a small label row under a pair; no new visual design. The hub public fixture under `tests/fixtures/hub_public/` is frozen: never regenerate it; add a second small fixture only if a hub test needs extras.

### D-04 Case-number side-car text join with a coverage line (PKG-04)
- New optional `--text-sidecar <file>` for `eureka run` (or a mapping key; planner decides, one way only): a CSV or JSON keyed by the record id with a text column. When a record's assembled text is below the engine's thin-text threshold and the side-car has text for that id, the side-car text is appended (not substituted), and the record is marked `text_source: sidecar`.
- The run summary prints one coverage line in numbers: records total, records with own text above threshold, records filled from the side-car, records still thin (dropped). The manifest records the side-car file hash.
- The public catalog text for this partner exists in the room as the Phase 1 input corpus (2,106 distinct case numbers measured on 2026-10-29). Building that side-car file from the room is NOT repo work and is NOT part of this phase's commits; the phase ships the mechanism and a documented format. A synthetic side-car is used in tests.

### D-07 Carry-in bundle and launcher (owner ruling 2026-10-29, plan 04, requirement PKG-07)
- "One click" for an enclave machine means one folder and one script, not an installer binary: a torch-sized single binary per operating system is large, unsigned and the first thing a locked machine refuses. Plain files with hashes are what an enclave can vet.
- Builder: `scripts/build-partner-bundle` (a thin entry over a module in `src/mindrian_eureka/`), run on the owner's machine, which MAY use the network to fetch the `uv` binary and wheels for the target platform; the bundle it writes is fully offline. Targets: `linux-x86_64`, `windows-x86_64`, `macos-arm64`; one bundle folder per target under `dist/`. The model folder is copied from a local path and is never downloaded by the builder unless `--allow-model-download` is passed.
- Bundle contents: the `uv` binary for the target, a wheel folder or uv cache that satisfies `uv sync --extra modern-encoder --extra hub-gate --offline` for the target, the Eureka source at the current commit (`git archive HEAD`), the model folder, `examples/mappings/technology-audit-export.json`, a `sidecar/` folder with a README and the format (the partner's own side-car file is dropped in by the owner before hand-over), `docs/partner-run-guide.md`, `BUNDLE-MANIFEST.json` (sha256 and byte size of every file, engine version, source commit, build time, target, builder inputs), and the launchers `start.sh` and `start.ps1`.
- Launcher sequence, identical on every platform: `eureka doctor` (stop on any FAIL and show the printed fix), `eureka run <input> --mapping <bundle mapping> --text-sidecar <sidecar if present> --output <output>`, `eureka hub <output>`, then open the hub page in the default browser. Parameters: input folder, output folder; defaults next to the bundle. Re-running on a new export is the same click. No network call anywhere in the launcher.
- Docker variant, optional (`--docker`, built only when `docker` is on the builder's PATH): `docker save` of the existing image into `eureka-image.tar` plus `start-docker.sh` / `start-docker.ps1` that `docker load` the tar and run it with `--network none` and the input, output and model folders mounted. Same manifest, same hashes.
- Test on this machine: build the `linux-x86_64` bundle into a temp folder from the local uv cache (no network in the test), verify every manifest hash against the file bytes, run `start.sh --dry-run` (prints the sequence, executes nothing) and run `eureka doctor --json` from inside the bundle in a subprocess (skip with a stated reason when the local model is absent). Other targets are not built in the test; the plan states that.
- Names: the bundle is `eureka-partner-bundle-<target>`; no person's name and no partner name beyond what the repo already names. Every page and output the bundle produces keeps `candidate, not verified`.
