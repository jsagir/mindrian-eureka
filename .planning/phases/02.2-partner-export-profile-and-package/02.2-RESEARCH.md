## Summary

The whole phase is additive on a path that already exists. `eureka run` reads a CSV through a JSON mapping (`run/mapping.py`), builds `Record` objects (`run/contracts.py:104-127`), runs the two engines on every record (`run/pipeline.py:286-300`), projects each engine's result into one fixed pair shape (`run/project.py:152-278`), writes canonical JSON (`run/output.py`) and a manifest (`run/manifest.py`). The hub reads those files back with hash checks and a strict but key-tolerant reader (`hub/reader.py`), builds a payload (`hub/model.py:204-440`) and renders it (`hub/page.py`, `hub/assets/authored/*.js`). Every new field this phase needs (an outcome class and extras on a record, a `pair_class` and extras on a pair, a side-car hash in the manifest) has one natural attach point in that chain, and at each point unknown keys are either validated by a schema the project owns (the mapping) or ignored by the consumer (the hub reader reads by `.get`). PROVEN.

Three facts decide the plan. First, both engines' pairs pass through exactly one shared place after ranking: `project_unusual_pairs` and `project_wording_and_meaning` in `run/project.py`, called back to back in `pipeline._write_outputs` (`pipeline.py:313-326`). One function that attaches `pair_class`, `left_extras` and `right_extras` to a projected document, called twice there, serves both engines and any future engine that uses the same projection. The runner's own pair dict (`opportunity_pairs/runner.py:135-166`) is the wrong place: the projection copies only a fixed field list (`project.py:177-198`), so anything added in the runner is dropped. Second, the hub reader already loads a pair file that carries extra keys (`reader.py:242-266` reads named keys only) and a corpus line that carries extra keys (`reader.py:209-216`); the smallest change is optional fields with defaults on `RunPair`, `Record` and `PayloadPair`, plus one filter key in `hub-core.js:30`. Third, the recorded wording params hash `bea4c100c2013300` is pinned by `tests/test_run_engines.py:360-364` and comes only from `engines.wording_params` (`engines.py:361-392`); the new settings belong in `settings.run` and `inputs` of the manifest (`pipeline.py:336-341`, `corpus.py:135-144`), which no fingerprint covers, so no recorded hash moves. PROVEN.

Two pitfalls need a decision up front. The text cleaner decodes entities only when the cell has a tag-like start (`textclean.py:13,26-31`); an abstract such as `It&rsquo;s` with no tag stays undecoded under `html: "auto"` (PROVEN by a probe in this session). Set `"html": "always"` in the shipped mapping entry; the schema allows it (`mapping.py:54`) and no code changes. And the record id is prefixed with the CSV file stem (`corpus.py:471`: `f"{id_base}/{id_part}"`), so a side-car keyed by `case_number` must be joined on the raw id cell before the prefix, or the join silently matches nothing.

**Primary recommendation:** Add three optional mapping keys (`outcome_rule`, `carry_columns`, and nothing for the side-car), one CLI flag `--text-sidecar`, optional fields on `Record`, one `attach_pair_classes()` in `run/project.py` called twice in `pipeline._write_outputs`, optional fields on `RunPair`/`PayloadPair`, one new filter key in the hub, and conditional output keys everywhere so a run without a rule writes the same bytes as today.

### Pattern 1: Conditional output keys keep the default run byte-identical
**What:** Write `pair_class`, `*_extras`, `text_source`, `extras`, `text_sidecar`, `pair_classes` only when the feature is active; never write `null`.
**When to use:** every new key in `corpus_lines` (`output.py:106-117`), the projected pair, the manifest sections and the summary JSON (`pipeline.py:130-148`).
**Why:** `tests/test_run_project.py:254` pins the default key set; `tests/test_run_determinism.py` compares two runs of the same input, and the frozen fixture pins its own bytes; CONTEXT D-02 says `pair_class` is absent, not null.

### Pattern 2: Dataclass defaults for additive contract fields
**What:** `Record`, `_Candidate`, `RunPair` gain fields with defaults at the end; `PayloadPair` gains `NotRequired` keys.
**Why:** `Record(...)` is constructed positionally by keyword in `corpus.py:620-630`, `reader.py:209-216`, `tests/hub_support.py` and many tests; defaults keep all of them compiling. Frozen dataclasses with `field(default_factory=dict)` are already the project idiom (`mapping.py:95-97`).

### Pattern 3: One shared post-projection step for every engine
**What:** `attach_pair_classes(doc, records)` in `run/project.py`, pure function on plain dicts (the module rule at `project.py:9`: no numpy, no engine call).
**Why:** both engines and any future engine that uses `_file_shell` get the class and extras from one place; the runner and `hsi_reference` stay untouched (D-02).

### Anti-Patterns to Avoid
- **Changing the runner document** (`engines.py:278-292`): moves `task_snapshot_id` and breaks "byte-identical by default".
- **Adding keys to `wording_params`** (`engines.py:375-392`): moves `bea4c100c2013300` and fails `tests/test_run_engines.py:360-369`.
- **Joining the side-car on `Record.id`**: the id carries the file-stem prefix (`corpus.py:471`); join on the raw id cell.
- **Putting cleanup logic in the mapping**: D-01 says extend `textclean.py` if needed; here `html: "always"` is enough.
- **Regenerating `tests/fixtures/hub_public/`**: pinned by `tests/test_hub_public_fixture.py:68-119`.
- **A new colour or shape for the class chip**: `docs/brand/hub-design-decisions.md:25` reserves colour; reuse `.hub-chip`.

## Common Pitfalls

### Pitfall 1: Entities without tags are not decoded
**What goes wrong:** `abstract` holds `It&rsquo;s` with no `<p>`; the text keeps the literal entity.
**Why:** `html: "auto"` runs the cleaner only when `looks_like_html` matches `<[A-Za-z/!]` (`textclean.py:13`; `corpus.py:400`). PROVEN by probe.
**How to avoid:** `"html": "always"` in the shipped mapping entry (`mapping.py:54` allows it). Add a test with an entity-only cell.
**Warning signs:** `&` followed by letters and `;` in `corpus/records.jsonl`.

### Pitfall 2: `;` list and `>` in `topics`
**What goes wrong:** `Parent > Topic;Parent > Topic` reads as one line of symbols.
**Why:** text columns are copied as cells; no list handling exists (`corpus.py:425-430`).
**How to avoid:** keep `topics` as a labelled text block (D-01); the engines tokenize words, so `;` and `>` are harmless. The hub escapes `<` and `>` inside JSON strings (`hub/contracts.py:402-410`). No code change.

### Pitfall 3: `Y`/`N`, the third value `no translational award`, and counts in text cells
**What goes wrong:** a rule written as `== "Y"` misses `y`, ` Y`, `Yes`; `licenses > 0` on a blank or non-numeric cell raises.
**Why:** cells are raw strings; `value_maps` only touch text columns (`corpus.py:390-399`).
**How to avoid:** the rule evaluator trims and upper-cases flags; parses counts with `int()` after `strip()`, treats blank or unparsable as 0 and counts them into one warning ("N cells in column X were not whole numbers; treated as 0"). `had_follow_on` is not in the rule and is only carried. Document the rule grammar in the mapping schema (`columns`, `any_of` with `equals` or `greater_than`).

### Pitfall 4: Blank money and date cells in the label row
**What goes wrong:** the hub shows `funding_total:` with nothing after it.
**How to avoid:** carry the raw strings as D-03 says, but the label row renders only non-empty cells; the payload keeps them all.

### Pitfall 5: The 50-character threshold counts labels, not the title
**What goes wrong:** a row with only labels and three words passes the threshold because `"Problem solved:\n"` counts; a row with a long title and no body is dropped because the title is excluded (`corpus.py:577` tests `candidate.text`, not `model_text`).
**How to avoid:** apply the side-car check on the same `candidate.text` value, before the drop (`corpus.py:574-582`), and print the coverage line from that loop. Do not change `MIN_BODY_CHARS` (`limits.py`, shared with `hsi_reference.py:159`).

### Pitfall 6: Side-car id join and file-stem prefix
**What goes wrong:** zero records filled.
**Why:** `Record.id` is `"<csv-stem>/<sanitized id>"` (`corpus.py:471`); the side-car is keyed by `case_number`.
**How to avoid:** join on the raw id cell (`corpus.py:440`) before sanitising; report "side-car ids that matched no record: N" as a warning so a wrong key column is visible.

### Pitfall 7: Small classes and the percentile gate
**What goes wrong:** the run returns pairs, but zero of class `cross`, and nobody notices.
**Why:** the gate is per engine over all pairs (`algorithm.py:337`); class counts are a post-hoc split.
**How to avoid:** print the three counts per engine in the summary (D-02) and warn when a class has fewer than 2 records. The existing warnings below 5 records (`corpus.py:594-598`) and below 10 eligible pairs (`runner.py:122-123`) stay.

### Pitfall 8: Privacy in tests, examples and docs
**What goes wrong:** a real case number, inventor, company or person name lands in a fixture or example.
**How to avoid:** synthetic ids `C00001`..`C00012`, synthetic answers, synthetic licensee lists never carried (`carry_columns` excludes the three company-list columns and the four people columns by D-03); a test loads the shipped mapping and asserts those seven columns are in neither `text_columns`, `extra_fields` nor `carry_columns`; `tests/test_run_cli.py:236` and `tests/test_run_corpus.py:805` already guard that error text never holds cell text. The partner guide names "JHTV" only.

```python
# run/project.py (new, plain dicts only, module rule at project.py:9)
def attach_pair_classes(doc, records):
    classes = {r.id: r.outcome_class for r in records if r.outcome_class}
    if not classes:
        return doc
    counts = {"cross": 0, "open_open": 0, "licensed_licensed": 0}
    extras = {r.id: dict(r.extras) for r in records}
    for pair in doc["pairs"]:
        left, right = classes[pair["left"]["id"]], classes[pair["right"]["id"]]
        pair_class = "cross" if left != right else f"{left}_{left}"
        pair["pair_class"] = pair_class
        pair["left_extras"] = extras[pair["left"]["id"]]
        pair["right_extras"] = extras[pair["right"]["id"]]
        counts[pair_class] += 1
    doc["counts"]["pair_classes"] = counts
    return doc
```
